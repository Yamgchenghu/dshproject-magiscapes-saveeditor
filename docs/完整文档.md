# 第一部分 · 使用手册

适用存档：`Magi Scapes`（UE5.3，`GenerativeGame`）
本说明对应版本：**2026-11-14 修复营地移动后的构建**

---

### 一、它能做什么

| 页面 | 能改的东西 |
|---|---|
| 概览 | 存档名称、玩家名 |
| 玩家 | 角色名、当前生命 / 生命上限、当前魔力、饥饿、体温 / 体温上限、毒素 / 毒素上限、声望经验 |
| 背包 | 每件物品的数量、按物品 ID 新增物品 |
| NPC | 名册（招募 / 驱逐 / 删除已驱逐记录）、NPC 名字、NPC 背包、NPC 战斗属性 |
| 记忆 | NPC 每条记忆的**类型**和**优先级** |
| 世界 | 世界时间、营地名称 / 等级 / 位置、商店刷新天数、传送石激活、宝箱物品 |
| 地图 | 按区块改地形图块、改放置物朝向 |
| 模块 | 浏览全部 146 个模块的原始字段 |
| 资料库 | 物品名表、NPC 名表（全存档通用） |

**它不会做的事**：不会重写整个存档。每次保存只改动你实际编辑过的那几个字节，
其余部分原样保留。这也是它敢直接写你正在玩的存档的原因。

### 二、第一次使用

#### 1. 先备份

程序**每次保存都会自动备份**，备份在：

```
%LOCALAPPDATA%\GenerativeSaveEditor\backups\<存档文件夹名>\<时间戳>\
```

但第一次用还是建议手动复制一份整个 `GameSave_1` 文件夹。

#### 2. 关掉游戏

**必须关掉。** 游戏在保存或退出时会重写全部 146 个模块文件，你在编辑器里改的
东西会被整个覆盖掉。程序检测到游戏在跑会警告你。

#### 3. 打开存档

点左上角「打开存档」，选中这个文件夹：

```
%LOCALAPPDATA%\GenerativeGame\Saved\SaveGames\Steam_76561199629133762\GameSave_1
```

注意选的是 **`GameSave_1` 文件夹本身**，不是里面的 `Primary`。
选对之后程序会记住，下次启动自动打开。

#### 4. 改，然后保存

改完点右上角「保存」。标题栏出现 `*` 表示有未保存的改动。

保存很快（几十毫秒），不会再出现之前那种「未响应」。

### 三、每个页面怎么用

#### 概览

- **存档名称**：游戏里存档列表显示的名字。
- **玩家名**：和「玩家」页的角色名是同一个值，改一处两处都变。

下面「文件状态」是自检信息，不用管。如果「解析无告警」不是满的，
说明这个存档有程序读不懂的地方——不影响你改别的东西。

#### 玩家

**生命与状态**这一组可以随便改。「全部回满」会按上限把当前值填满。

几个需要注意的：

- **声望等级是只读的**。游戏会按声望经验自己重算等级，直接改等级没用。
  想提等级就改**声望经验**。
- **没有「魔力上限」这个字段**。存档里玩家只有 `MaxHealth` / `MaxHeat` /
  `MaxToxin`，没有 `MaxMagic`。这不是漏做，是游戏本身就没存。

#### 小队

一行一个人，长这样：

```
编号1  NPC：[流云（Liuyun）      ▼]   ↑ ↓ ✕
编号2  NPC：[『七号』（Seventh） ▼]   ↑ ↓ ✕
编号3  NPC：[（空）              ▼]   ↑ ↓ ✕
[+ 新增]              [人数上限 3…]
```

下拉框里是这个槽位能放的人。选另一个就换人；如果选的人已经在别的槽里，两个槽会对调，不会出现同一个人占两格。

`↑` `↓` 调顺序，`✕` 移出。「+ 新增」加一个空槽，自动填进第一个还没在队里的人。

#### 小队、已招募、营地 NPC 是三个不同的名单

这个特别容易搞混，页面上专门写了一段说明：

| 名单 | 存在哪 | 意思 |
|---|---|---|
| **小队** | `Player__Players` 的 `FollowNpcIDs` | 真正跟着你走的人 |
| **已招募** | 营地模块的 `CampsiteRecruitedNPCIds` | 加入过营地的人，可以很多 |
| **营地 NPC** | `CampsiteAINPCIds` | 常驻营地的人 |

改小队**不会**影响招募名单。反过来也一样。

> 有个坑：流云（Liuyun）在小队里，但不在「已招募」名单里。所以小队页的候选人是拿整个 NPC 表算的，不是从招募名单推出来的。

#### 突破 3 人上限

游戏自带界面只给 3 个位置。但存档里 `FollowNpcIDs` 就是个字符串数组，长度字段只有元素个数，**没有专门的人数字段**——文件格式本身不限制人数，只有游戏自己的逻辑限制。

点「人数上限 3…」可以改：

- **4 人已实测通过**：第 4 个人正常跟随，对话菜单里有「离开小队」，存读档都不掉
- 6、10、40… 用的是同样的字节结构，理论上一样，但**没人实测过**
- 上限最高可填 64（纯粹是防手滑，不是格式限制）

超出上限时页面顶部会提示，但**编辑器不会替你删人**。超限状态下删人、调序都正常，只是不能再加。

设置存在 `%LOCALAPPDATA%\GenerativeSaveEditor\party.json`。

#### 背包

每行是一件物品：左边名字，右边数量。

- **双击某一行**才能改数量与词条（等级 / 稀有度 / 前缀 / 后缀）。
- **「全部堆满」**会把每件物品补到它自己的堆叠上限。
- **数量不能超过堆叠上限**。超了游戏读档时会自动砍回上限，看起来就像「改了被回退」。
- 空槽位显示为「（空）」。
- 点「新增物品…」可以往背包里加东西，有两种方式：
  - **按名字搜**：从资料库里挑。
  - **按 ID 加**：直接填物品 ID。适合资料库里没有的物品。

物品名字的优先级是：**存档里物品自带的显示名 → 资料库 → 原始 ID**。
所以看到一串数字说明这个名字目前没人知道，不是 bug。

#### NPC

上半部分是名册，点某个 NPC 进去看详情。

**名册的三种状态**，和游戏里一致：

| 状态 | 含义 |
|---|---|
| 营地 NPC | 住在你营地里的人 |
| 已招募 | 被你招募、但还没住进营地 |
| 已驱逐 | 被你赶走的人 |

被驱逐的 NPC 默认**不显示在 NPC 列表里**，但记录还在。想彻底清掉就去
「世界」页的「管理招募 / 驱逐…」——删掉之后只能靠 ID 重新招回来。

名册上的按钮：

- **全员回满**：把所有 NPC 的生命补满。
- **全员好心情**：把所有 NPC 的心情拉满。
- **招募…**：从已知 NPC 里挑一个招募。
- **按 ID 招募…**：直接填 NPC ID 招募。
- **踢出…**：把某个 NPC 赶走。

**NPC 详情**里能改：

- **名字**
- **背包**（四类：普通物品、武器、饰品、装备），双击改数量和词条
- **战斗属性**：最大生命、最大魔力、体质、智力、速度等

内置 NPC 的中文名来自官方 wiki，显示为中文；你自己招募的 AI 角色显示它在存档里的名字。

#### 记忆

这个页面读的是 NPC 记忆模块。左边选 NPC，右边按天列出它的每条记忆。

**能改两个字段**：

- **类型**：任务 / 击杀 / 死亡 / 采集 / 心情下降
- **优先级**：数值越小越优先

**参数是只读的**，显示成 `key = value` 的样子。

为什么参数不让改：存档里每个参数的编码格式都不一样——有的是标准文本前缀，
有的是裸字符串，长度还各不相同。硬改会把整条记录写坏，导致这个 NPC 的记忆全部丢失。
宁可只读，也不给你一个看着能改、实际会毁档的框。

#### 世界

- **世界时间**：游戏内经过的小时数。
- **营地名称 / 等级**：直接改。
- **上次升级天数**：游戏按「今天 − 上次升级天数」判断能不能再升级，
  把它调小就能立刻再升一级。
- **营地位置**：点「改营地位置…」弹窗填格子坐标。见下面第五节，这块有坑。
- **名册**：显示营地 NPC / 已招募 / 已驱逐三组，点「管理招募 / 驱逐…」改。
- **商店刷新天数**：商店下次刷新的日子。
- **传送石**：列出 17 个传送石，**双击一行**切换激活状态。
- **宝箱**：宝箱散在 120 多个区块里，**要点一下扫描**（约 10 秒）才会列出来，
  之后能改物品数量。

#### 地图

两个卡片：

- **地图数据（只读）**：统计信息。
- **按区块编辑**：选一个区块，看它的地形和放置物。

地形图上：

- 只画**你改过的**格子，没动过的地皮不画（画了就是一片糊）。
- **石墙画成石头灰，木地板画成木棕，占位格画成黑色。**
- 右边有图例，颜色和名字对应。
- 点一个格子能看到它的图块编号，能改图块。

放置物能改**朝向**（`bTurn90`）和**旋转档位**（`RotateIndex`）。

##### 三个视图开关

地图上方有三个开关，可以任意组合：

| 开关 | 作用 | 什么时候用 |
|---|---|---|
| **只看营地** | 视图裁到营地范围，格子放大到 14px | 看自己铺的地皮（默认开） |
| **整块显示** | 铺满整个 150×150 区块，格子 5px | 看这块区域整体长什么样 |
| **显示全部层** | 层 9、10 也当普通图层：实色、可点、可改 | 想读/改基底记录 |

**「只看营地」和「整块显示」是互斥的**：关掉只看营地会自动打开整块显示，
因为不裁到营地就必须看整块，否则只是换了个裁剪框，看不出区别。

**关于「显示全部层」**：

存档里层 9、10 是**基底记录**，覆盖的格子远多于你真正铺过的地皮
（营地 6241 格里，9/10 覆盖 2061 格，你实际铺的只有 121 格）。
所以默认把 9/10 淡化成背景，不然你铺的木地板、田地会被整片盖住。

打开「显示全部层」之后，9/10 变成实色、可以点选、可以改图块，
图例里会标成「层9（基底，可编辑）」。

**格子的叠放顺序**：层 10 在最底，然后 9、4、5、7、8。
层号大的不一定盖在上面——9/10 层号最大，但它们是基底，必须垫底。
早期版本按层号排序，结果基底把地皮全盖住了，看起来一片土色。

**点了开关以后页面不会跳走**：这三个开关都会重建整张地图卡片，
以前重建完会把页面滚回最上面，地图正好在卡片下面，于是看起来像「点了没反应」。
现在重建会记住你滚到的位置，切到别的页面才回到顶部。

##### 按层统计

地图卡片最下面列出**层 0 到层 10** 的逐层明细：

```
层 7      322 条 · 322 格 · 4 种图块集
层 9      2061 条 · 2061 格 · 1 种图块集
层 0      无
```

每一行是「这个层在这个区块里有多少条记录、覆盖多少格、用了多少种图块集」。
存档里没有这一层就写「无」——层 0–3、6 在整份存档里一次都没出现过，
所以永远显示「无」，那是正常的。

**「条」和「格」不是一回事**：同一格可能被同一层写了好几次，
所以条数 ≥ 格数。层 9/10 在营地那块正好一格一条，两个数字才一样。

「铺过地皮的格子」那一行会标明**含不含基底层**：
关掉「显示全部层」时统计的是你真正铺的（121 格），
打开后把 9/10 也算进去（2061 格）。

#### 模块

列出全部 146 个模块，点进去能看每个字段的原始值。

这个页面是给你**查东西**用的，不是日常改东西用的。里面很多字段改了游戏也不认。

#### 资料库

两个表：物品（210 种）和 NPC（54 个）。这两个表是**全局**的，
所有存档共用一份，存在：

```
%LOCALAPPDATA%\GenerativeSaveEditor\catalog.json
```

**自动更新**：每打开一次存档，编辑器会把那个存档里见过的物品和 NPC 自动并进
资料库，**不需要再手动点「扫描」**。只在真的发现新东西时才写文件，重复打开
同一个存档不会反复改盘。

**导出 / 导入**：资料库页上有两个按钮。

- **导出资料库…** 把整份资料库打包成一段密文，约 29 万字符。可以「复制全部」
  发到聊天窗口，也可以「另存为文件…」存成 txt。
- **导入资料库…** 把别人给你的密文粘进去，或「从文件读取…」。

密文的格式是：JSON → UTF-8 → Base64 → 每个字符转十六进制 → 再转成二进制位串
→ 用「1~2位叠数计量法」压成数字和字母。这只是一种让内容在聊天窗口里看起来像
乱码的包装，**不是加密**，不要用它保护敏感信息。

**导入是合并，不是覆盖**：只补充本地还没有的 ID，你已经录入的名称不会被别人的
覆盖。重复导入同一份密文不会产生重复行。导入时会自动剔除不合规的行（8 位 AI
物品、6 位随机码 NPC、名字等于 ID 的行）。

**收录规则**（这几条是硬规矩）：

- 只存**名字**和 **ID**，不存别的。
- **物品 ID 是 7 位数字**的才收录。8 位的是 AI 生成的道具，不收录。
- **NPC ID 里带小写字母**的才收录（内置 NPC）。6 位全大写加数字的是玩家自己
  招募的随机码，不收录。
- **名字和 ID 一样的行一律不收**——这种行没有任何信息量。

**扫描范围**：玩家身上**全部九个**物品数组（背包、快捷栏、装备、饰品、武器、
手持、皮肤、载具、丢弃、声望奖励）加**每个 NPC 的背包**。早先只扫了前五个，
导致玩家丢掉或放进载具的物品永远进不了资料库。

**箱子里的物品和地图放置物不收录**——它们的数据里都不带 `ItemConfig`，游戏里
本来就查不到它们的名字。地图放置物的字段叫 `PlaceableItemID`，挂在地形地图里，
整个结构没有任何名称信息。想给这类 ID 起名，去「背包」页点「录入物品名称」，
或者直接在资料库页手动录入。

**名字的来源是 `ItemConfig.Explain`**。有些物品的 `Explain` 是一整句描述，
例如 `【武器】：技能展开后，手持长矛与五柄平行长矛会随普通攻击一同突刺。`，
编辑器会保留分类前缀并截到第一个逗号/句号，得到 `【武器】技能展开后`；
`雪原中常见的石头，与平原石头颜色上有差别。` 会变成 `雪原中常见的石头`。
这比显示裸 ID 有用，但它**不是**游戏里的正式短名——游戏没给这类物品短名。

还有少数物品的 `Explain` 是英文资产名（`Steak`、`Twine`、`Wool`、`SandTile`
之类）。存档里没有中文名可查：`ItemConfig.ItemName` 是本地化 GUID，不是明文，
只有游戏运行时才能解析。这类条目会在资料库里显示英文名，**在「录入物品名称」
里输入 ID 就能改成中文**，改完立刻在所有页面生效。

看到资料库里缺东西是正常的，说明还没人见过那个物品的显示名。

### 四、为什么有些东西改不了

编辑器有一条底线：**不确定的字段不给你改**。

具体是这些：

| 字段 | 为什么只读 |
|---|---|
| 声望等级 | 游戏按经验重算，改了会被覆盖 |
| NPC 记忆的「参数」 | 编码格式不统一，硬改会毁掉整条记忆 |
| 物品的稀有度 / 词条 | 和物品模板绑定，改单个字段会不一致 |
| 地图的「层 9 / 层 10」 | 这不是地皮，是「这格被加载过」的标记，改了没意义 |
| 大部分模块字段 | 游戏不读，改了不生效 |

**判断标准**：如果一个字段改了游戏不认，那它就不该出现在可编辑的位置上。
让你改一个不会生效的东西，比不让你改更糟。

### 物品编辑：官方道具与 AI 道具不是一回事

双击背包里的物品会打开编辑窗。**能改什么，取决于这件物品是谁造的。**

#### AI 生成的物品（ID 8 位，如 20000003）

**完整定义就存在存档里**，游戏读档时原样读取。所以下面这些都能改，改完游戏里立刻生效：

- **名称**、**描述**（物品浮窗里那段说明文字）
- **属性**：攻击力、最大生命、暴击率、攻击范围、攻击速度、总伤害加成……每一项都有中文名
- **词条**：等级、稀有度（0 白 / 1 绿 / 2 蓝 / 3 紫 / 4 橙 / 5 红）

#### 官方道具（ID 7 位，如 3010046）

**只能改数量。** 这是刻意的限制，不是没做。

原因：官方道具的 `ItemConfig` 只是游戏数据表（`DT_Items`）的一行**缓存副本**。游戏读档时会用数据表重新构建它，所以：

- 改名称、描述、属性、词条 → 被数据表覆盖，**改了不生效**
- 数值格式和数据表对不上 → **可能坏档**

所以官方道具的编辑窗只留一个数量输入框，其余字段只读显示，方便你查看。

#### 为什么有些属性是灰的

带**等级曲线**的属性（例如 `3010046` 的攻击力，曲线行 `3010046_PhysicalDamage`），游戏读档时会按词条等级重新计算，`Value` 只是个倍率。直接改数值会被覆盖——这就是以前「改了不生效」的真正原因。

灰色的那几项不能改，旁边会写明是哪条曲线。**要提升它们，请改下面的词条等级。**

#### 关于「改了不生效」的其他原因

1. **游戏正在运行**：游戏退出时会用内存数据覆盖整个存档。编辑器检测到游戏在跑会提示你。
2. **数量超过堆叠上限**：游戏读档时会把 `Count` 夹回 `MaxStack`，看起来就像被回退。编辑器会直接拒绝这种输入并告诉你上限。
3. **带曲线的属性**：见上一节。


### 五、营地位置：改了游戏不认的原因（已修）

这是这一版修的最重要的 bug。

#### 现象

把营地从 `格(100,74)` 改到 `格(120,90)`，编辑器里读出来确实变了，
但进游戏营地还在原地。

#### 原因

存档里营地不是一个点，是**一整块地皮**：

| 字段 | 内容 |
|---|---|
| `AllCampsite[0].CampsiteCoord` | 锚点，9 个数 |
| `CampsiteCells` | 营地实际占的 6 241 格（79×79） |

锚点里有些字段是**真数据**（`DetailX` / `DetailY` / `DetailIndex` / 世界坐标），
有些是**占位符**：

```
CellIndex   = -1
DetailIndex = -1
LocalPosition / WorldPosition = (0, 0, 0)
```

这 6 241 格里，`CellIndex`、`DetailIndex`、两个位置向量**全部**是这种占位值——
一个都不是真数据。游戏在运行时自己按 `DetailX` / `DetailY` 算出来。

**旧版的做法是错的**：它把这 6 241 格的占位符全部填上了算出来的真实值。
填完之后，这块地皮的形状和游戏自己写出来的存档不一样了，游戏判定数据不一致，
直接把整个营地改动丢掉。

也就是说：**是「补全」这个动作本身把移动弄坏的，不是漏补。**

#### 现在的做法

只平移 `DetailX` / `DetailY` 两个数，占位符**原样保留**。

验证（对副本，营地 6 241 格从 `X 61..139 / Y 35..113` 移到 `X 81..159 / Y 51..129`）：

| 检查项 | 移动后 |
|---|---|
| `DetailIndex = -1` | 6 241 / 6 241 ✅ |
| `CellIndex = -1` | 6 241 / 6 241 ✅ |
| 位置全零 | 6 241 / 6 241 ✅ |
| 格范围 | 正确平移 20 / 16 格 ✅ |
| 锚点 | 同步更新 ✅ |

来回移动三次（`(100,74) → (120,90) → (70,50) → (100,74)`）坐标全部精确回到原位。

#### `CellIndex` 为什么不动

`CellIndex = BiomeY × 17 + BiomeX`。营地是 `Biome(7,4)`，所以是 `4×17+7 = 75`。

这个值只跟**区块**有关，跟格子在区块里的位置无关。同一个区块内怎么移动，
`CellIndex` 都不该变。跨区块移动才会变，而当前版本不支持跨区块移动。

### 六、常见问题

**问：改完数字，界面上还是老值，是不是没改成？**

这是 15:24 之前几个版本的 bug，现在已修。当时是「写入对、回读错」：
新值确实写进了存档，但界面刷新时读的还是内存里的旧副本。
所以那会儿「保存后重开存档」能看到变化，只有「改完当场看」看不出。

现在这几处都能改完立刻看到新值：存档名、营地名、玩家名、玩家最大生命、
NPC 血量、NPC 记忆的类型和优先级、背包数量、地形图块。

如果你用的还是老版本，重新复制一份 `存档编辑器.exe` 覆盖即可。

**问：营地为什么只能填 39–110？**

因为营地是一整块 **79×79 的地皮**，以你填的格子为中心。一个区块只有 150×150 格，
所以中心点最小只能到 39（此时地皮正好贴住区块左上角），最大只能到 110
（正好贴住右下角）。超出这个范围地皮会伸到区块外面，**游戏不会报错，只是
不理这个位置**——看起来就是「改了没动」。

所以程序现在直接拒绝越界值并说明原因，而不是写进去让你白折腾。

**问：改了数量，进游戏被改回去了。**

多半是超了堆叠上限。游戏读档时会把超上限的数量砍回上限。
另外确认改之前游戏是关着的。

**问：打开存档很慢。**

不会。打开时只解析 23 个可编辑模块，116 个地图区块是按需载入的。
如果慢，检查是不是存档在机械硬盘上。

**问：能改别人的存档吗？**

能，只要是同一个游戏版本的存档。但不同版本的字段可能对不上，
程序会显示解析告警。

**问：改坏了怎么办？**

1. 程序自动备份在 `%LOCALAPPDATA%\GenerativeSaveEditor\backups\`。
2. 游戏自己也有版本快照，在 `GameSave_1\Versions\`。
3. 最坏情况：删掉 `GameSave_1` 文件夹，游戏会新建一个空存档
   （但你的进度就没了，所以还是先备份）。

**问：为什么地图上大片区域是空白的？**

因为只画改过的格子。存档只记录**改动过**的地皮，没动过的不存。
所以空白 = 原始地形。

**问：闪退了怎么办？**

崩溃日志在 `%LOCALAPPDATA%\GenerativeSaveEditor\errors.log`。
如果这个文件是空的，说明进程是被系统或访问违例杀掉的，不是程序异常。

## 一·五、小队（`FollowNpcIDs`）

### 位置

```
Player__Players.sav
└─ PlayersData              MapProperty
   └─ <SteamID>             StructProperty
      ├─ FollowNpcIDs       ArrayProperty  (InnerType = StrProperty)  ← 小队
      ├─ InventoryItems     ArrayProperty
      ├─ HotbarItems        ArrayProperty
      └─ ...
```

`FollowNpcIDs` 是个纯字符串数组，每项一个 NPC ID：

```
i32 count
重复 count 次:  i32 len + FString
```

没有其他字段，没有人数上限字段，没有槽位结构。**槽位顺序 = 数组顺序**，所以调序就是改数组顺序。

### 实测数据

| 存档 | 小队 |
|---|---|
| GameSave_1 | `Liuyun`, `SnowWillow`, `NARR0D`（3 人） |
| GameSave_2 | `Liuyun`（1 人） |

### 为什么 4 人能行

游戏读取这个数组时不校验长度——它只是把每个 ID 都当成跟随者实例化。3 这个数字只存在于**界面层**（UI 只画 3 个槽位、只允许从界面加到 3 个）。

所以：

- 写 4 个 → 游戏读出 4 个跟随者 → 正常
- 第 4 个人的交互菜单显示「离开小队」→ 说明游戏确实把他当小队成员
- 存读档一轮后仍在 → 说明没有其他逻辑把它裁掉

### 实现上的两个坑

**坑一：`Parse()` 不是幂等的。**

`SaveModule.Parse()` 每次调用都重建整棵属性树。之前拿到的 `SaveProperty` 引用全部变成孤儿，上面挂的待写入值静默丢失。

```csharp
// 错：每次调用都重新解析，把上次的编辑丢掉
var m = slot.Find("Player__Players");
m.Parse();
var prop = m.FindProperty("FollowNpcIDs");

// 对：只在没解析过的时候解析
if (m.Properties.Count == 0) m.Parse();
```

**坑二：`MarkDirty` 只暂存，`Value` 还是旧的。**

写完立刻读 `Value` 会读到磁盘上那份，看起来像写入失败。

```csharp
// 错：读的是解析时的旧值
var ids = (List<object?>)prop.Value;

// 对：优先读暂存值
var ids = prop.PendingValue is { } pending
    ? DecodeStringArray(pending)
    : (List<object?>)prop.Value;
```

这两个 bug 是同一类：**改了之后读回旧数据**，表现出来就是「改了不生效」。

### 上限校验只拦增加

一开始校验写成 `if (list.Count > SlotLimit) reject`。这在超限状态下会把人锁死：40 人、上限 3，删一个还剩 39，39 > 3，任何操作都被拒——用户没法执行提示里让他做的事。

改成：

```csharp
if (list.Count > SlotLimit && list.Count > current) reject;
```

只拦「变大」，不拦「变小」和「不变」（调序）。

### 四、词条系统（本轮新破解）

这是之前完全没读到的模块。

#### 三层词条包

每件物品的 `ItemSaveData` 下有 **3 个词条包**：

| 包 | 字段名 | 说明 |
|---|---|---|
| 基础词条 | `EquipmentAffixData.BasePackage` | 物品生成时掷出的固有词条 |
| 附魔词条 | `EquipmentAffixData.EnchantPackage` | 附魔台加上去的 |
| 卷轴词条 | `EnchantScrollAffixData` | 卷轴加上去的，**在 `EquipmentAffixData` 外面** |

每包 6 个字段：

```
bValid     (Bool)   是否生效
Seed       (Int)    随机种子
Level      (Int)    词条等级
Rarity     (Int)    稀有度
PrefixId   (Name)   前缀 ID
SuffixIds  (Array)  后缀 ID 列表
```

#### 稀有度

`0=白 1=绿 2=蓝 3=紫 4=橙 5=红`

#### 实例：大棒骨

| 包 | 状态 | 等级 | 稀有度 | 前缀 | 后缀 |
|---|---|---|---|---|---|
| 基础 | ● 生效 | 65 | 蓝 | `Prefix_Sword_Crit`（精准） | `Expansion_Status_WeaponReach`（武器·攻击距离）<br>`Expansion_Legend_Event_Offense_26`（传奇·事件·进攻） |
| 附魔 | ● 生效 | 35 | 蓝 | `Prefix_Sword_AttackSpeed`（迅捷） | `Expansion_Status_WeaponFury`（武器·狂怒） |
| 卷轴 | ○ 未生效 | 1 | 白 | `None` | 空 |

> 所以「词条有几个」这个问题的答案是：**3 个包**，但实际生效的词条条目有 5 条（基础包 1 前缀 + 2 后缀，附魔包 1 前缀 + 1 后缀）。

#### 词条名称：为什么只能"拆词"，以及哪两个是官方名

游戏自己的名称表**取不出来**，原因很硬：

- `GenerativeGame-Windows.pak` 的索引是 **AES 加密**的（UE5 v11，footer `bEncryptedIndex = 0x4F`），解析出的 offset/size 是乱码；
- 真正的字符串在 `.ucas` 里，是 **Oodle 压缩**的，游戏目录**不带 Oodle 解码器 DLL**；
- 全盘搜索 `Precise` / `Swift` / `Prefix_Sword_Crit` / `Critical Chance` 等，`.pak` 与 `.ucas` 里**零命中**。

所以编辑器改成**按 ID 自身的词根拆词**，逐段翻译后拼起来，例如：

| ID | 读法 |
|---|---|
| `Prefix_Sword_Crit` | 剑·暴击 |
| `Expansion_Status_WeaponReach` | 状态·武器·攻击距离 |
| `Expansion_Legend_Event_Offense_26` | 传奇·事件·进攻 |
| `AffixV2Aligned_Shadow_High` | 暗影·高级 |
| `Suffix_SpecSword_CritRate` | 剑专精·暴击率 |

**但有两个是官方确认的**，不是拆出来的：游戏里物品名「精准迅捷的大棒骨」正好是
两个前缀名直接拼接，因此

- `Prefix_Sword_Crit` = **精准**（Precise）
- `Prefix_Sword_AttackSpeed` = **迅捷**（Swift）

这两条在编辑器里优先于拆词结果。其余词条若要换成官方译名，可以编辑
`%LOCALAPPDATA%\GenerativeSaveEditor\affix-names.json`（`{"ID": "名字"}`），
自定义名优先级最高，改完重启编辑器生效。

> 词条的**具体数值**（比如"暴击率 +3%"）不在存档里，是由 `Seed` + `Level` + `Rarity`
> 在运行时掷出来的。所以编辑器只能改掷骰的输入，不能直接写死某条数值。

#### 技术难点（已解决）

`SuffixIds` 看着像 `ArrayProperty`，实际上 `ArrayElements` 是 `null`、`Value` 是个纯字符串列表。原始布局就是 `i32 个数` + 连续的 FString。之前走通用数组编码会报「暂不支持编辑 ArrayProperty」，现在专门为它写了读写函数，可以整块重写。

`bValid` 是 `BoolProperty`，**值存在标签头里而不是值区**，声明 size 是 0。之前补丁器完全没处理这种类型，现在单独走单字节改写路径。

#### 营地等级可以改

`CampsiteSave__CampsiteSave` → `AllCampsite[0].Level`，是个普通 IntProperty，游戏直接读。编辑器把它做成「营地等级」数字框。

#### 「上次升级天数」是升级的闸门

同一个结构里还有 `LastUpgradeWorldDay = 65`。游戏判断「能不能再升一级」用的是**今天 − 上次升级日**，今天是第 5 天而上次升级是第 65 天，所以正常情况下要等到第 65 天之后。

把 `LastUpgradeWorldDay` 调小（比如改成 0），下次读档就能**立刻再升一级**。编辑器在这一行下面直接标了「今天是第 N 天」，免得你算。

> 注意它和 `Level` 是两件事：改 `Level` 是直接跳级，改 `LastUpgradeWorldDay` 是解除升级冷却。两个都改就是「先跳级、再马上还能升」。

#### 营地位置可以改，而且是三个字段一起改

`AllCampsite[0].CampsiteCoord` 有 9 个字段，同一个位置存了两遍：

```
WorldType     EnumProperty    ETopDownWorldType::Surface
LocalPosition StructProperty  [147264, 86400, 0]      ← 世界坐标（浮点）
WorldPosition StructProperty  [147264, 86400, 0]      ← 同上
BiomeX/Y      IntProperty     7 / 4                   ← 大区块
CellIndex     IntProperty     75
DetailX/Y     IntProperty     100 / 74                ← 地表格子
DetailIndex   IntProperty     11200                   ← 打包索引
```

**只改一半会出问题**：游戏用格子索引决定加载哪块地，用浮点坐标决定相机和物理落点。所以编辑器改位置时把 `DetailX`、`DetailY`、`DetailIndex`（= `Y × 150 + X`）、`LocalPosition`、`WorldPosition` 五处**一起重写**，保证营地不会同时出现在两个地方。

界面里输入的是格子坐标（0–4095），浮点坐标按「1 格 = 1024 单位」自动换算。

`CampsiteCells` 是营地实际占的格子（这个存档是 `(139,113)` 一格）。这一项编辑器**只读**——改它要连带重算地形上的建筑占位，风险远大于收益。

#### 名册：招募 / 驱逐 / 删除是三个不同的动作

`CampsiteSave__CampsiteSave` 顶层有三个字符串数组，各自独立：

| 数组 | 本档内容 | 含义 |
|---|---|---|
| `CampsiteRecruitedNPCIds` | `Aurelia`、`Alex`、`Seventh`、`SnowWillow` | 住在营地里的人 |
| `CampsiteKickedNPCIds` | `1XAP7L`、`SYEMVW` | 被驱逐过、还能在名册里看到 |
| `CampsiteAINPCIds` | `YEDK65`、`513SMT`、`NARR0D`、`43NTG3`、`G1A9JX`、`VWYH1F`、`BC0QGS`、`X4D2U2` | 营地自带的 AI 角色 |

- **招募**：从「全部 NPC」里挑一个，加进 `Recruited`，同时把它从 `Kicked` 里移除（不然会两边都在）
- **驱逐**：从 `Recruited` 移到 `Kicked`。只是换名单，记录还在
- **删除**：从 `Kicked` 里彻底去掉

这三个动作在编辑器里是「营地名册」对话框的三个页签 + 三个按钮，对应你提的「已招募的可以增加、驱逐；已驱逐的可以删除」。

#### 6.5.5 采集点：存档里不存在

我专门找过采集点（植物、矿脉、可采资源），结论是**这类数据不在存档里**。

依据有两条：

1. 每个 `GenMap__SurfaceChunk_N` / `GenMap__UndergroundChunk_N` 的顶层**只有两个字段**：`Index`（IntProperty）和 `Cell`（StructProperty，5 个子字段）。没有任何按格子记录的资源节点表。
2. 全档按 `Gather / Harvest / Resource / Collect / Node / Plant / Tree / Ore / Spawn` 关键字扫过一遍，命中的 91 处全是无关的（`PickDropID`、`bCanAISpawn`、`SpawnVFX` 之类），没有一处是「这个采集点已被采走」的状态。

唯一和采集沾边的是 `CollectionSystem__CollectionData.ItemCollectedCounts`——那是**图鉴里的累计收集计数**（401 条，key 是物品 ID），不是地图上的点位。

所以采集点应该是游戏按 `MapSeed`（4002）在运行时生成的，存档只记种子。这也就意味着**没有可改的东西**：想刷新采集点只能换种子或等游戏自己的刷新周期。

#### 6.5.6 已探索区域 = 迷雾位图

「已探索区域」就是 6.5.1 那三张迷雾位图，不是独立的区域列表。`RevealAll` 填 255 即等于「全部探索过」。

#### 6.5.7 按区块编辑（可视化）

每个区块可以单独打开，只解析它自己（0.2–1.3 秒），不用扫全世界（28 秒）。

**格子坐标怎么来**

区块里的地形改动记在 `ModifiedOptimizedDataByDetailIndex`，key 是一个整数 `DetailIndex`。它的含义是：

```
DetailIndex = Y × TerrainSize + X        （TerrainSize = 150）
```

反解 `X = DetailIndex % 150`、`Y = DetailIndex / 150`。校验过：用 `150` 解出来的格子，和放置物坐标的重合率是 1755/7751，明显高于其他候选尺寸（128 → 1454、160 → 1439、100 → 1086），且每个 key 正反算完全一致。

**图层语义**

每个格子的地形由最多 5 层组成，`LayerID` 只取 5 / 7 / 8 / 9 / 10：

| 图层 | 记录数（SurfaceChunk_18） | 图块集种类 | 说明 |
|---|---|---|---|
| 5 | 306 | 5 | 装饰 |
| 7 | 2498 | 8 | 地面 |
| 8 | 3165 | 6 | 墙体 |
| 9 | 7551 | 1（固定 3-5） | **基础层** |
| 10 | 7751 | 1（固定 6-0） | **基础层** |

关键发现：**每个图块集只出现在固定的一个图层上**。所以图块集编号编码的是图层归属，不是材质。层 9、10 几乎每格都一样、不含信息，画图时被剔除。

**可视化怎么画的**

- 只画改过的格子（有非基础层的），未改的留白——这样改过的区域会形成一个可辨认的形状
- 颜色按图层给：层 8 灰（墙体）、层 7 棕（地面）、层 5 绿（装饰），同一层内按图块编号微调明暗
- 占位格（`PlaceableItemID = "OCCUPIED"`）涂纯黑
- 宝箱用橙色方框标出
- 自动裁掉四周空白，让内容填满视口
- 格子放大到 20 px 以上时，格子上直接写出图块编号

**关于「石墙画灰、木墙画棕」**

做不到精确区分，原因说清楚：图块集编号 → 材质名的对照表在游戏的 `GenerativeGame-Windows.ucas` 里（`BiomeTileSetTableRow` / `GetTileSetTableRowNameByTileSet`），但 `.ucas` 是压缩归档、内部路径是哈希的，`.pak` 的索引也读不出名字。所以存档只给出编号，给不出「这是石墙」。

替代方案：编辑器里可以**自己给图块集起名和配色**（「给图块集起名/配色」按钮），填一次存到 `%LOCALAPPDATA%\GenerativeSaveEditor\tilesets.json`，所有存档通用。在游戏里看一眼哪片是石墙，把对应编号命名成「石墙」并选灰色，之后就永久生效。

**能改什么**

- 放置物：旋转 90°（`bTurn90`）、旋转档位（`RotateIndex`）
- 地形：任意一格的图块集（`TileSetIndex`）与图块（`TileImageIndex`）

写入验证（`--selftest`，发布版 exe 实测 exit 0）：

```

放置物 SurfaceChunk_18 68, 107 (4010432): 旋转90 False → True
重新打开: 区块地形 图 99（期望 99）→ 通过
          区块旋转 True（期望 True）→ 通过
```

只有 `GenMap__SurfaceChunk_18.sav` 一个文件发生变化。

#### 6.5.8 加载区块为什么会闪退（已修）

症状：切区块的时候偶尔整个窗口消失。

原因查清了，是三个叠在一起的问题，都出在界面层，不是存档坏了：

**1. 后台读完回来时窗口可能已经没了**

读区块是后台线程干的，读完要回界面线程刷新。原来的写法是：

```csharp
if (IsDisposed) return;
BeginInvoke(new Action(() => Navigate("map")));
```

`IsDisposed` 只挡住「已销毁」，挡不住「句柄还没建好」和「正在销毁」这两种状态——这两种情况下 `BeginInvoke` 会抛 `InvalidOperationException`。而这个 `ContinueWith` 里没有 try，异常直接逃出去。WinForms 里逃出消息循环的异常会**结束进程**，看起来就是闪退。

**2. 一次异常 = 整个程序没了**

没有任何全局兜底。任何一处漏掉的异常都能让程序直接退出。

**3. 快速切区块有竞态**

连续切 A → B，如果 A 读得慢，A 的结果会盖掉 B 的，界面显示错区块。这个不崩，但会让人以为「点错了」。

**修法**

- 所有「后台读 + 回界面」统一走一个 `RunBackground` 辅助函数：工作本身、回写界面、渲染结果三层各自 try，任何一层失败只影响这一次刷新
- `BeginInvoke` 前同时检查 `IsDisposed || Disposing || !IsHandleCreated`
- 加了请求序号 `_chunkToken`，过期的读取结果直接丢弃
- 加了全局兜底：`Application.ThreadException`、`AppDomain.UnhandledException`、`TaskScheduler.UnobservedTaskException` 全部接管。真出意外就弹一个「出错了（但没退出）」，同时把堆栈写进 `%LOCALAPPDATA%\GenerativeSaveEditor\errors.log`

**顺带发现的一个「假崩溃」**

`GenMap__UndergroundChunk_61` 这个区块只有 **1,638 字节**，顶层只有 `Index` 和 `bUnderground` 两个字段，**没有 `Cell`**——游戏对没生成过的区域只写一个空壳。读它会返回 `null`，原来的界面拿到 `null` 就显示一片空白，看着像加载失败。

现在会明确说明：

> 「GenMap__UndergroundChunk_61」里没有地形数据。游戏对没生成过的区域只写一个 1.6 KB 的空壳（只有区块编号，没有格子数据），这种区块本来就没有东西可看、可改。换一个区块就好。

116 个区块里只有这一个是空壳。

**加载中的提示**

读一个区块要 0.2–1.3 秒，原来这段时间界面没反应。现在：

- 区块选择行下面会出现一条浅蓝提示条：**「正在读取 GenMap__SurfaceChunk_18…」**
- 右上角状态栏同步显示
- 读取期间**不显示上一个区块的图**，避免把旧图当成新图
- 底部说明「读取期间不显示旧图，避免把上一个区块当成这个区块」

##### 6.5.8.1 第一轮没修好：真正的根因是句柄和内存（2026-11-14 再查）

上面那轮改完，用户反馈「地表 3\* 4\* 5\* 还是闪退」。复查发现上面三个问题都真实存在、也确实该修，但**都不是主因**——因为它们都会留下托管异常，而 `errors.log` 里**一条记录都没有**。

没有日志只有一种解释：**进程是被系统直接杀掉的**，托管异常根本没机会抛出来。顺着这条线找到了两个真正的杀手，都在绘制环节。

**1. 每个格子新建一支画笔，GDI 句柄被耗尽**

`ChunkGrid.OnPaint` 原来的写法是逐格绘制，每个格子 `using var b = new SolidBrush(...)`：

```csharp
for (int y = 0; y < _h; y++)
    for (int x = 0; x < _w; x++) {
        using var b = new SolidBrush(ColorFor(top, _palette));   // ← 每格一支
        g.FillRectangle(b, rect);
    }
```

一个区块是 150 × 150 = **22 500 格**。每画一次就是 22 500 支画笔。GDI 对象虽然有 `using` 会释放，但重绘频率远高于释放速度（鼠标移动、滚动、窗口刷新都会触发重绘），句柄数很快撞到 Windows 的默认上限（每个进程 10 000 个 GDI 句柄）。**撞上就是进程直接死亡，没有异常、没有日志。**

这也解释了为什么偏偏是 3\* 4\* 5\* 这些区块：它们是地形最密的一批。

**2. 每打开一个区块，就永久留在内存里**

`SaveSlot.LoadModule` 会把解析过的模块缓存进 `Modules` 列表，之后再也不释放：

```csharp
var m = SaveModule.Load(path);
Modules.Add(m);      // ← 永远留着
```

而区块模块非常大——`GenMap__SurfaceChunk_76` 有 **24 821 条地形**，`_18` 有 **21 271 条**，每条地形是一组属性对象。一个区块解析后占几十到上百 MB。用户来回切十几个区块，进程就涨到几个 GB，32 位地址空间或系统内存一满，同样是**直接被杀**。

**修法**

- 画笔按**颜色**分组：先把 22 500 个格子归到「颜色 → 矩形列表」的字典里（通常只有几十种颜色），然后用 `Graphics.FillRectangles` 一次画完一种颜色。整个重绘过程的画笔数量从 22 500 支降到**几十支**
- 颜色计算加缓存：`(图层, 图块编号) → 颜色` 查表，不再每格重新推导
- `SaveSlot` 新增 `ReleaseModule(name)`：切区块时把上一个区块从缓存里丢掉（**有未保存修改的模块不丢**，避免丢工作）
- `LoadChunk` 增加重入保护：上一次还没读完就不接受新的请求，避免连点堆叠

**验证方法（这次是量化验证，不靠肉眼）**

新增 `--stress` 模式和离屏绘制测试，把最重的 8 个区块（含 24 821 条地形的 76 号）连续加载 5 轮，每轮统计进程的 GDI 句柄数和内存：

| | 修复前 | 修复后 |
|---|---|---|
| GDI 句柄（5 轮后） | 持续上涨，撞上限即死 | **稳定在 3 个** |
| 内存（5 轮后） | 726 MB → **2 688 MB**，线性增长 | 743 MB → **1 398 MB**，不再增长 |

单次绘制耗时 2–20 ms，24 821 条地形的区块也是 14 ms，所以卡顿和崩溃都不是解析慢造成的。

**结论**：`errors.log` 为空是关键线索——托管异常会留日志，进程被杀不会。以后遇到「闪退但没有 errors.log」，先查 GDI 句柄和内存，不要继续在异常处理上找。

### 七、版本快照机制

`Versions\v_<版本号>\` 下每个目录含一个 `Complete.marker` 和一份 `Modules\`（146 个 `.sav` 副本）。

`Manifest.sav` 里：

#### 7.1 「改数量被回退」的真正原因（2026-11-14 查清）

用户报告改背包数量会被回退。逐层排查后，编辑器本身的写入链路是**完全正常**的：

| 验证层 | 方法 | 结果 |
|---|---|---|
| 核心层 | 直接改 `Count` 属性 + `SaveAll` + 重新打开 | 通过 |
| 页面重读 | 标记脏值后再 `ReadPlayer`（模拟切页） | 通过，仍是同一批属性对象 |
| 真实对话框 | `ShowDialog` + 键盘输入 + 回车 + `Apply` | 通过 |
| 「保存修改」按钮 | 走 `SaveChanges()` 全流程 | 通过 |
| 发布版 exe | 对副本跑 `--selftest` | 通过 |

真正的原因有三条，都不是编辑器写坏：

1. **超过堆叠上限会被游戏夹回。** 每件物品有 `MaxStack`（沙漠石头 999、烤肉排 99）。写进 1200 是能落盘的——我实测磁盘上确实是 1200——但游戏读档时按 `MaxStack` 夹回 999，从玩家角度看就是「改了没用」。**这才是最常见的那个。**
2. **游戏运行时保存等于白改。** 游戏退出时会用内存里的整份数据覆盖 `Primary\Modules\*` 和 `Versions\v_*\Modules\*`。存档在用户反馈前 18 秒被整体重写了一次（10:37:06），所有模块的时间戳都一样，这就是游戏自己写的。
3. **版本快照会被游戏优先读取。** `Manifest.ActiveVersion` 指向的那个 `Versions\v_*` 目录才是游戏实际读的那份。只改 `Primary` 而不改快照，游戏下次读档拿到的仍是旧数据。

对应的修复：

- **超上限拦截**：对话框里填超过 `MaxStack` 的数会当场弹窗说明，并把输入框夹回上限，而不是写一个注定活不过一次读档的值。
- **保存后回读校验**：保存完成后重新从磁盘打开存档，逐个比对该物品的数量。只要有一个对不上，就明确报「数值没有落地」并提示先关游戏，而不是显示「保存成功」。
- **测试工具加保护**：`--uitest` 和 `--selftest` 一样，指向真实存档时直接拒绝执行（退出码 2）。

> 教训：**「保存成功」不等于「数值生效」。** 只比对文件时间戳和字节数会漏掉这两种情况，必须把值读回来比。

### 八、文件格式（技术说明）

#### 容器层

每个 `.sav` 不是裸 GVAS，而是分块压缩容器：

```
[8 字节魔数 c1 83 2a 9e 22 22 22 22]
[41 字节块头]   ← blockSize=131072、压缩/原始长度各写两遍
[zlib 压缩流]   ← 解压后 ≤ 131072 字节
[下一块…]       ← 重复直到文件末尾
```

解压后的载荷开头有 8 字节（两个 `u32`）：第一个是「总长−4」，第二个是 GVAS 长度，改写时必须重算。

`Manifest.sav` 是例外：**裸 GVAS**，没有容器包装。

#### 属性层

标准 UE 属性标签：

```
FName 名字 | FName 类型 | i32 大小 | i32 数组下标 | 类型附加信息 | u8 有GUID | [16 字节 GUID]
```

关键坑（都已处理）：

1. **StructProperty 即使 `hasGuid=0` 也带 16 字节 GUID 块**。
2. **数组元素只有第一个带 16 字节 GUID 块**，后续元素直接接在上一个的 `None` 之后。
3. **数组内层标签的 size 是整个数组的大小**，不是单个元素的大小。
4. **元素内部是单一属性列表**，遇到 `None` 就结束。若继续扫描，元素里的二进制数据会伪装成属性标签，把后续元素全吞掉。
5. **FText 有两种布局**，需按 size 反推跳过字节数。
6. **中文用 UTF-16LE**（长度为负）。只放行 ASCII 会让所有中文称号读成空串。
7. **`BoolProperty` 的值在标签头里**，声明 size 是 0，改动是单字节替换。

#### 编辑器的写入策略

**不整体重序列化，只做字节级精准改写。**

这是刻意的选择：格式里有太多「部分理解」的结构（双属性列表、两种 FText、每元素 GUID），整体重写随时可能把没读懂的数据写坏。精准改写能保证**没动的字节一个都不变**。

实测证据：把快捷栏第 1 格数量从 1 改成 6，保存后

- 未压缩载荷：**374,273 → 374,273 字节**（长度完全一致）
- 不同的字节：**1 个**（`01` → `06`）
- 磁盘文件却从 30,864 变成 31,600 字节——**纯粹是 zlib 压缩率波动，不是数据膨胀**

#### 声望等级为什么是只读

游戏判断等级是**根据经验值重算**的，直接改等级字段下次读档会被覆盖。所以界面把它显示成只读信息，只让你改经验。

#### 安全机制

- 只做**字节级精准改写**，不做整体重序列化
- 改动后自动修复整条父级 size 链
- 保存前重新解析，出现**新增**告警就中止
- 覆盖前自动备份到 `%LOCALAPPDATA%\GenerativeSaveEditor\backups\`
- 保存后**从磁盘重新读取**并把结果回显给你看
- 未改动的模块保持**字节完全一致**

### 十、资料库的收录规则

`catalog.json` 只存**名称 + ID**（外加来源路径），不存任何数值。

两条过滤规则，每次加载都会重新筛：

| 规则 | 原因 |
|---|---|
| 物品 ID 必须是 **7 位数字** | 8 位的是 AI 生成的临时道具，不是正式物品 |
| NPC ID 必须**含小写字母** | 6 位纯大写+数字的是玩家招募的随机 NPC |

被排除的东西仍然能改背包，只是不进资料库。遣散过的招募 NPC 仍然可以按 ID 重新招回来。

### 十一、已知限制

| 限制 | 原因 |
|---|---|
| 玩家没有 `AttributeMap` | 玩家的血/魔上限是 `PlayersData` 里的独立字段，和 NPC 那套结构不同 |
| 官方 NPC 没有属性卡 | `Aurelia` / `Alex` / `Seventh` / `SnowWillow` 既没有 `BaseAttribute` 也没有 `AttributeMap`，数值在游戏本体 |
| 五项基础属性改了不动血量 | 那五项是生成时的输入，游戏运行时读的是 `AttributeMap`（详见第五节） |
| 营地占格（`CampsiteCells`）只读 | 改它要连带重算地形建筑占位，风险大于收益；能改的是营地锚点坐标 |
| `NPCMemory` 有 7 条告警 | 嵌套数组内层类型解析不了，只读噪声，不影响其他模块 |
| 新增物品只能复制已有物品 | 不凭空捏造配置，找不到配置会明确报错 |
| 部分词条 ID 不可读 | 有些存的是本地化 key（32 位 GUID），需要游戏的 `DT_LanguageText` 才能翻译 |
| 小箱子没有空槽 | 小箱子只写实际用到的槽位（可能只有 1 格），加物品前需要先清空一格 |
| 宝箱扫描要 10 秒 | 需要解压并解析 117 个 1–3 MB 的地图区块；结果会缓存，改动后才重扫 |
| 地图区块有大量解析告警 | 原始存档里就有（逐模块对比确认不是写入造成的），编辑器不把它们计入健康统计 |
| 放置物没有「已开启」标记 | 存档里不存在这个字段，开箱状态只能从宝箱内容间接判断 |
| 采集点改不了 | 存档里根本没有采集点数据，游戏按种子在运行时生成（详见 6.5.5） |
| 图块集不能自动认成「石墙/木墙」 | 图块集→材质名的对照表在游戏 `.ucas` 里，路径哈希、索引压缩，读不出名字。只能按图层给默认色，或在编辑器里手动给图块集起名配色（详见 6.5.7） |
| 地形图不能画出真实画面 | 游戏贴图在 `.pak` 里，存档只存图块编号。画的是「哪格改成了哪个图块」，不是地形渲染图 |
| 有一个区块是空壳 | `GenMap__UndergroundChunk_61` 只有 1.6 KB，没生成过，没有地形可看（详见 6.5.8） |
| 区域（Zone）只读 | 已解析出来但没做编辑界面，改了用途不明，风险大于收益 |
| 传送石短 ID 会重复 | 两块不同的石头都叫 `TS_SF_1_1`（坐标 70,122 和 54,69），所以列表把坐标并进编号列一起显示 |
| 「全部隐藏」会清掉探索记录 | 填 0 等于整层没走过。界面加了二次确认，误点会丢这一层的探索进度 |

### 十二、对话框布局：三个被裁掉的对话框（2026-11-14 修复）

有一类 bug 只在**特定文字长度**下才出现，代码看一百遍也看不出来，截图一眼就看见。这一轮修了三个。

#### 12.1 改营地位置：文字压住了输入框

**现象**：`格 X` 那一行的数字被上面「当前：…」的第二行盖住了，看起来像是输入框里塞了乱码。

**原因**：对话框用的是绝对坐标，`当前：` 那行只给了 40 px 高。
坐标文字是 `ETopDownWorldType::Surface · 区块(7,4) 格(100,74) · 世界坐标(147264,86400)`，
在 390 px 宽里要折成两行，实际需要约 56 px。多出来的 16 px 正好压到 y=46 的数字框上。

**修法**：整段换成 `TableLayoutPanel` + `AutoSize`。每一行的高度由内容量出来，
`当前：` 那行 `MaximumSize` 限制宽度后自动折行，行高跟着长，后面的行自动下移。
窗口高度在 `Load` 里按 `table.PreferredSize.Height` 算，并夹到屏幕工作区内。

#### 12.2 放置物：底部两行和按钮被切掉

**现象**：`旋转 90°` 复选框只露出半个，`旋转档位` 和确定/取消按钮完全看不见。

**原因**：窗口 `Height = 260` 写死，卡片里 4 条信息 + 复选框 + 档位 + 按钮实际需要约 340。

**修法**：`Load` 里按 `card.Bottom + 12 + 边框高度` 重算窗口高度。

#### 12.3 确定/取消按钮跑出卡片右边

**现象**：修完高度后按钮露出来了，但「取消」右半边被裁。

**原因**：按钮坐标写死 `x=306`，而卡片内宽约 350，`306+80=386` 越界了。

**修法**：改成从行宽右边缘往左排（`cancel.Left = width - cancel.Width`），
并挂 `Resize` 重算，这样换字体或改卡片宽度都不会再错位。

地形对话框有完全相同的问题，一并修了。

> **经验**：这几个 bug 都是「固定像素 + 中文折行」造成的。
> 凡是内容长度会变的对话框，一律用 `TableLayoutPanel` / `AutoSize` / `PreferredSize` 计算，
> 不要手写 `Location`。并且在截图流程里给每个对话框加一张渲染图——
> 这类问题只能看出来，想不出来。

### 十三、营地位置为什么改了不动（2026-11-14 查清并修复）

> ⚠️ **本节结论已被第十七节推翻，保留只为记录排查过程。**
> 这里认为「营地不动是因为 `CampsiteCells` 的格子没跟着平移」，并据此让代码
> 把每一格的 `DetailIndex`、`CellIndex`、`LocalPosition`、`WorldPosition` 一并「补全」。
> 后来的实测证明：这些字段在真实存档里**全是占位符**（`-1` 和 `(0,0,0)`），
> 真正有数据的只有 `DetailX` / `DetailY`；「补全」它们反而让游戏彻底不认这块地皮。
> **正确做法见第十七节：只改 `DetailX` / `DetailY`。**

**现象**：把营地从 `格(100,74)` 改成 `格(120,90)`，存档里读出来确实变了，但进游戏营地还在原地。

**原因**：存档里营地不是一个点，是**一整块地皮**。

`CampsiteSave__CampsiteSave` 里有两份相关数据：

| 字段 | 内容 |
|---|---|
| `AllCampsite[0].CampsiteCoord` | 营地的**锚点**：世界类型、世界坐标、区块、格子坐标、格子编号 |
| `CampsiteCells` | 营地**实际占的每一格**，共 **6 241 格**（79 × 79 的一块） |

原来的 `SetCampsitePosition` 只改锚点那 9 个数，`CampsiteCells` 里那 6 241 格原封不动。
游戏建营地是**按格子来的**，不是按锚点——锚点只是给人看的坐标摘要。
所以锚点改了、格子没动，游戏照旧把营地摆在老地方。

**顺带发现的一个读取 bug**：`CampsiteCells` 的存储方式很反常——它是「一个数组元素，
里面平铺着 6 241 段坐标」，不是 6 241 个数组元素。原来的读取代码把整段当**一个**坐标读，
所以界面里营地格子数一直显示 1。现在按 `WorldType` 分段，正确读出 6 241 个。

**修法**

1. 读取时按 `WorldType` 把平铺的属性列表切成一段段坐标，`Cells` 现在是真的 6 241 个
2. 写入时算出锚点的位移 `(dx, dy)`，然后把 `CampsiteCells` 里**每一格**都平移同样的量，
   同时重算每格的 `DetailIndex` 和世界坐标
3. 只要有一格移不动就整体报错，不允许出现「锚点动了、地皮没动」这种半截状态

**验证**（对副本，锚点从 (120,90) 移到 (128,85)）

| | 改前 | 改后 | 位移 |
|---|---|---|---|
| 锚点 | 格(120,90) | 格(128,85) | (8, −5) |
| 占格范围 X | 61..139 | 69..147 | (8) |
| 占格范围 Y | 35..113 | 30..108 | (−5) |
| 占格数量 | 6 241 | 6 241 | 不变 |

锚点位移、占格位移、格子总数三者一致，`DetailIndex` 仍满足 `DetailY × 150 + DetailX`。

**关于 `CellIndex`**：一度怀疑是漏改 `CellIndex` 导致营地不动。查证后否定了——
营地锚点是 `Biome(7,4) / CellIndex 75 / 格(120,90)`，玩家的出生点是
`Biome(7,4) / CellIndex 75 / 格(100,76)`，两者**同一个 CellIndex、不同格子坐标**，
说明 `CellIndex` 只跟区块走、与格子无关。而且 `GenMap__*Chunk_*` 的 `Cell` 结构里
根本没有 `BiomeX/BiomeY/CellIndex` 字段（只有 `TerrainSize`），这三个数是营地自己的，
无法从区块反推。所以 `CellIndex` 保持不动是正确的。

##### 6.5.8.2 第三轮：真正杀死进程的是「在自己事件里销毁自己」（2026-11-14 终修）

前两轮修完，用户反馈「地表 61 还是闪退」。这次把范围收窄到那个具体区块，
做了一件之前没做过的事：**用真实控件、走真实事件**，而不是直接调函数。

结果：把所有地表区块逐个用真实 `ChunkGrid` 全尺寸绘制（3 种格子大小 × 79 个区块），
**0 崩溃**；GDI 稳定 3 个，内存不涨。也就是说，绘制和解析都不是凶手。
那问题只能在「点击 → 重建页面」这条路上。

**根因**

地图页的区块下拉框长这样：

```csharp
combo.SelectedIndexChanged += (_, _) => {
    if (combo.SelectedItem is not ChunkPick pick) return;
    LoadChunk(pick.Module);          // ← 内部第一件事就是 Navigate("map")
};
```

而 `Navigate` 原来的写法是：

```csharp
foreach (Control c in _content.Controls.Cast<Control>().ToList())
    c.Dispose();                     // ← 把 combo 自己也 Dispose 了
```

于是发生的是：用户在 `combo` 里选了新区块 → `combo` 正在派发自己的
`SelectedIndexChanged` 消息 → 处理器同步调用 `Navigate` → `Navigate` 把 `combo`
**当场 Dispose 掉** → 消息派发返回时控件已经是野指针 → **访问违规，进程立即死亡**。

WinForms 里「在自己的事件处理中销毁自己」是未定义行为。它不会抛托管异常，
所以 `errors.log` 一直是空的——这也是前两轮一直找不到方向的原因：我一直在找异常，
而这条路径根本不产生异常。

**为什么偏偏是 61 这类区块**

因为只有**需要重新布局**的时候才会真的重建页面。61 号区块的地形从
`DetailIndex 53` 一直铺到 `21520`，几乎占满整个 150×150 区块，它的画布是
全尺寸的（1000+ px），滚动条状态和别的区块不同。地形集中在小范围的区块
（比如 35 号只在 1405..10767）画布小、布局变化小，未必走到同一条销毁时机。
换句话说：**不是 61 号有毒，是 61 号最容易踩中这个时序**。

**修法（两层，第二层才是根治）**

1. 下拉框的处理器不再同步调用 `LoadChunk`，改成 `BeginInvoke` 投递到消息队列，
   让 `SelectedIndexChanged` 先完整派发完，再重建页面
2. **`Navigate` 本身改成延迟销毁**：先把旧控件从容器里摘下来（`Controls.Clear()`），
   真正 `Dispose` 交给 `BeginInvoke`。这样无论 `Navigate` 被谁、在什么事件里调用，
   都不会销毁正在派发消息的控件。没有窗口句柄时（首次导航）退化为立即销毁，此时安全

第 2 条是关键：它把这个类问题一次性堵死，而不是只修下拉框这一处。
代码里其它 6 处「对话框关闭后调 `Navigate`」也顺带获得了保护。

**验证（这次走真实事件）**

新增测试：真开窗口，设置 `combo.SelectedIndex` 触发真实 `SelectedIndexChanged`，
并覆盖三种用户行为：

| 场景 | 结果 |
|---|---|
| 依次切换 61 / 35 / 38 / 47 / 59 / 55 / 18 / 76 / 94（13 次） | 全部成功，GDI 稳定 59–65 |
| **完全不等待**地连点 10 次（上一个还在解析就点下一个） | 全部成功，GDI 稳定 55–60 |
| 切区块 → 跳去「概览」→ 跳回「地图」，重复 3 次 | 全部成功，GDI 稳定 59–70 |
| 每次切换后内存 | 719 MB 稳定，不增长 |

三组测试里地表 61 各出现 4–6 次，均未崩溃。

**教训**：闪退 + `errors.log` 为空 = 进程被系统杀死，不是托管异常。
要查的方向是：GDI/内存耗尽、**在自己事件里销毁自己**、栈溢出、原生库崩溃。
前两轮都在异常处理上打转，方向错了。

##### 6.5.9 营地位置「无法赋新值」的三个真实原因（2026-11-14 修）

用户反馈：营地位置那一行**改不了新值**。查下来是三件事叠在一起，而且
前两件都是我自己上一版写进去的 bug。

**原因一：世界坐标公式算错了（差一个数量级）**

存档里营地的位置存了两份：一份是格坐标 `DetailX/DetailY`，一份是浮点世界坐标
`WorldPosition`。我原来假设「一格 = 1024 世界单位」，即 `World = Detail × 1024`。

用游戏自己写下的真值一验就露了：

```
游戏原始:  区块(7,4) 格(100,74)  →  世界坐标(147264, 86400)
```

`147264 / 100 = 1472.64`，`86400 / 74 = 1167.57` —— 两个轴系数还不一样，说明
既不是 1024，也不是简单的等比。把它拆成「区块 + 格」的全局格号才看得出来：

```
全局格 = (区块 × 150 + 格)     ← 150 就是每个区块的地形边长
X: 128 × (7×150 + 100) + 64 = 128 × 1150 + 64 = 147264   ✓
Y: 128 × (4×150 +  74 + 1)  = 128 × 675       =  86400   ✓
```

所以正确公式是：**一格 = 128 世界单位，X 取格中心（+64），Y 多算一格**。
我原来那个 ×1024 写进去之后，锚点和世界坐标自相矛盾，游戏自然不认。

**原因二：保存后内存里的值被丢掉了（这是「赋不进新值」的直接原因）**

`ClearDirty()` 原来的写法只把待写入的字节丢掉，**没有把新值变成当前值**：

```csharp
PendingValue = null;   // ← 新值扔了，Value 还是旧数字
```

于是保存之后再读，读到的永远是编辑前的老数字。用户看到的现象就是：
输入新值 → 点应用 → 那一行还是旧值 → 以为根本没法改。
（文件其实写对了，只是界面在骗人。这一点我用「保存后同槽重读」专门测出来了：
改前 `格(120,90)` → 改后仍显示 `格(120,90)`，但重新打开存档却是 `格(100,74)`。）

修法是让新值接管：`OriginalValue = PendingValue` 并把字节解码回 `Value`。
同时把 `ReadCoordFromList` 和 `I()` 改成读「有效值」而不是原始值，
这样未保存的编辑也能立刻显示出来。

**原因三：上一版把锚点移了，却没移动营地占格**

营地不是单点，它占 6241 格（79×79）。游戏是**按占格**放营地的。
我上一版只改了锚点，占格留在原地，于是锚点和占格中心对不上：

```
真实存档当时:  锚点 格(120,90)   占格中心 格(100,74)   ← 不一致
```

游戏按占格放，所以营地在游戏里一动不动 —— 看起来就是「改了没反应」。

**新增：一键修复**

现在打开「改营地位置」时，如果检测到锚点和占格中心不一致，会直接显示
一条橙色提示并给出「修复对齐」按钮：把锚点拉回占格中心（**不动地皮**），
同时按正确公式重写世界坐标。用户那份存档已经用这个逻辑修好了：

```
修复前  锚点 格(120,90)  世界坐标(122880,92160)   ← 我上一版写坏的
修复后  锚点 格(100,74)  世界坐标(147264,86400)   ← 与游戏原值完全一致，占格未动
```

**另外**：游戏运行时改存档一律无效（退出时用内存覆盖全部模块）。
编辑器载入和保存时都会检测并提示，但如果你在游戏开着的时候改，
看到的现象同样是「改了不生效」—— 这一条也请留意。

**验证方式**（全部在副本上跑，最后才动真实存档，动之前已整份备份到
`C:\dsh_build\LiveBackup_20261114_145151`）：

| 对话框内赋值（代码路径） | 2 个输入框均可写入，`0`/`4095` 边界正常 |

##### 6.5.10 「点保存未响应」：一次保存卡 16 秒

用户点了「保存修改」之后窗口直接变成「未响应」。这不是死锁，是真的在算。

**元凶：打补丁的算法在 3.4 MB 缓冲区上反复搬字节**

保存时要把编辑过的字段写回原始字节流。原来的写法是：

```csharp
var buf = new List<byte>(payload);      // 3.4 MB
foreach (var (offset, oldLength, bytes) in ordered)   // 按偏移从大到小
{
    buf.RemoveRange(offset, oldLength);  // ← 搬动后面所有字节
    buf.InsertRange(offset, bytes);      // ← 再搬一次
}
```

`RemoveRange` / `InsertRange` 每次都会把偏移之后的全部字节往前/往后挪一遍，
成本是 O(n)。营地的模块 `CampsiteSave` 有 **56169 个可编辑字段**
（6241 格 × 9 个字段），一次保存产生约 6 万次编辑，
累计搬移量是几十 GB —— 实测 **16.4 秒**。

计时证据（把保存拆开看）：

| 步骤 | 耗时 |
|---|---|
| `BuildPayload`（打补丁） | **16,390 ms** |
| 自检重新解析 | 42 ms |
| 压缩（Wrap） | 24 ms |
| 解压（Unwrap） | 5 ms |

也就是说 99.8% 的时间都花在那一个循环里，跟压缩、跟磁盘都没关系。

**改法：单遍线性重建**

编辑列表按偏移排序后，从头到尾只走一遍：把「这一处编辑之前没动过的字节」
整段 `Buffer.BlockCopy` 过去，再拷入新值，跳过被替换的旧值。
每个字节只被搬一次，复杂度从 O(编辑数 × 文件长度) 降到 O(文件长度)。

**16,390 ms → 28 ms（585 倍）**，而且输出**逐字节相同**：

```
新实现 BuildPayload     28 ms  sha=566E5DF5A55FE82F len=3439256
旧算法（对照）       20763 ms  sha=566E5DF5A55FE82F len=3439256
输出逐字节一致 —— 新实现只改了速度，没改结果
```

验证方式是把旧算法原样保留在测试里当「标准答案」，同一份编辑分别跑两套实现，
比对 SHA-256。不是「看起来对」，是字节级一致。

**另外两处也在拖慢**

1. **保存后的「保存完成」弹窗**是模态的，会一直挡住消息循环。
   用户走开没点它，窗口就一直「未响应」。改成页面顶部的绿色提示条，可关闭、不阻塞。

2. **保存后重新打开整个存档**只为刷新标题栏的「有未保存的修改」标记，
   这一步要重新解析 146 个模块，约 1.9 秒。现在改成只更新标记，
   因为 `SaveAll` 已经把待写入的字节提升为新的基准值，内存里的数据本来就是最新的。

**完整保存耗时（用户点一下按钮到界面恢复可操作）**

| 版本 | 耗时 |
|---|---|
| 修复前 | 6,177 ms（外加一个阻塞弹窗，实际是无限期卡住） |
| 只修补丁算法 | 2,424 ms |
| 再去掉模态弹窗 | 269 ms |

**验证**

| 测试 | 结果 |
|---|---|
| 新旧算法输出比对（SHA-256） | 逐字节一致 |
| 营地位置+名称+等级 三项一起改后保存 | 282 ms |
| 保存后页面显示 | 名称/等级/坐标 全部是新值 |
| 重新打开存档读磁盘 | 三项都是新值，已落盘 |

##### 6.5.14 按物品 ID 添加，以及它暴露出的写盘截断 bug

**需求：支持从物品 ID 的方式向背包添加物品。**

所以玩家知道 id 但没见过的物品加不进去。

**做法**

搜索框兼作 ID 输入框（`SearchPickerDialog.AllowFreeId`）：
输入的字符串不是任何一行时，按字面当作 ID 使用。
`Validate` 回调负责在确定之前挡掉不可用的 id。

**唯一不能放行的条件：找不到物品配置**

物品在存档里不是一个 id，而是一组字节：

| 字段 | 作用 |
|---|---|
| `ItemConfig` | 物品定义（结构体字节） |
| `ItemSaveData` | 实例数据（词条、耐久等） |
| `ItemID` | 7 位官方 ID |
| `Count` | 数量 |
| `EquipmentHandle` | 装备句柄 |

`ItemConfig` 无法凭空构造——它必须从某件真实存在的物品复制。
所以按 ID 添加的实际规则是：

> 只要**本存档或相邻存档的背包里**有这件物品，就能按 ID 加进来；
> 都没有，就无法添加。

对话框会在确定前直接说清楚这一点，而不是等注入失败再报错。

**顺带发现的严重 bug：一次编辑多个字段会让存档截断**

这个 bug 一直存在，只是之前没有触发它的编辑路径。
按 ID 添加一件物品会同时弄脏 4 个字段（ItemConfig / ItemSaveData / ItemID / Count），
于是暴露出来。

**症状**：注入成功后写盘，`Player__Players` 的玩家属性从 39 个掉到 20 个，
后面 19 个字段（含 `CurrentHotbarIndex`）凭空消失。读回时 `ReadPlayer` 直接空引用崩溃。

**根因**（`SavePatcher.Apply`）

每个脏叶子都要把自己的 delta 加到所有祖先的 size 字段上，并往 `edits` 里加一条修补记录：

```csharp
parent.DeclaredSize += delta;
edits.Add((parent.SizeFieldOffset, 4, BitConverter.GetBytes(parent.DeclaredSize)));
```

4 个叶子共享同一个祖先时，**同一个偏移被加了 4 条记录**。
应用阶段第 112 行：

```csharp
if (e.Offset < src) continue;   // overlapping edit already covered
```

后 3 条被当作重叠丢弃——但 `totalLength` 在之前已经把这 4 条全算进去了。
于是输出缓冲比实际写入的多出 12 字节，`outBuf.AsSpan(0, dst)` 把尾部截掉。

单字段编辑（delta 只有一条）永远碰不到这个 bug，所以之前一直没发现。
改玩家名、改数量这类操作只要一次只改一个字段就是安全的，
但「一次改多个字段」的路径（加物品、批量操作）必然损坏存档。

**修复**

size 字段修补改为按偏移去重，只保留一条、取最终值：

```csharp
var sizeEdits = new Dictionary<int, byte[]>();
...
sizeEdits[parent.SizeFieldOffset] = BitConverter.GetBytes(parent.DeclaredSize);
...
foreach (var kv in sizeEdits)
{
    if (edits.Any(e => e.Offset == kv.Key)) continue;
    edits.Add((kv.Key, 4, kv.Value));
}
```

**验证（9/9 通过）**

| 测试 | 结果 |
|---|---|
| 按 ID 注入（沙漠石头 ×5，第 5 格） | 通过 |
| 注入后玩家属性数不变 | 通过 39 |
| 不存在的 ID 被拒 | 通过 |
| 改名后属性数不变 | 通过 39 |
| 写盘后属性数完整 | 通过 39 → 39 |
| 写盘后物品还在 | 通过 第 5 格 1020051 ×5 |
| 写盘后名字生效 | 通过 |
| 全部 146 个模块可解析 | 通过 |

修复前同一测试的表现：重读属性数 **20**（应为 39）。

### 十四、地图为什么只显示了一小块：层 9/10 不是「改动」（2026-11-14 查清并修复）

#### 14.1 问题的样子

领地 79×79 共 6241 格，玩家在游戏里铺了大片木地板、田地、水池、牧场草，
但编辑器地图上只有零星几块，而且换个区块就完全对不上。玩家说
「修改的部分读的不全，这块是我的领地，改了很多地方的」。

#### 14.2 先纠正一个错误的结论

上一轮曾把层 9、层 10 当成「基底记录，可以忽略」，把它们排除在渲染之外。
营地所在的 `GenMap__SurfaceChunk_75` 里，层 9 和层 10 各有 2061 条记录，
覆盖的格子完全一致（交集 2061），而层 5/7/8 加起来只有 906 个不同格子。
于是得出「排除 9/10 会丢掉 56% 的格子」，又把它们加了回来，上色数从 906 变成 2061。

**这个推理是对的，但结论是错的**——2061 里有 1345 格在营地之外，
真正属于领地的只有 716 格，而这 716 格**一格都没换过地皮**。

#### 14.3 怎么证明的

拿区块 75 层 9 的主图块集（`2-*`，该区块出现最多的地面图块）当作本区原始地面，
逐格比对营地足迹内的 716 格：

| 情况 | 格数 |
|---|---|
| 层 9 图块集 = 本区原始地面 `2` | **716** |
| 层 9 图块集 ≠ 原始地面 | **0** |

也就是说，营地范围内所有带层 9 记录的格子，层 9 都还是原始地面。
层 9/10 记录的语义是「这一格被加载/保存过」，**不是「这一格被重新铺过」**。

再看全存档 98 个有地形的区块的覆盖率：平均只有 6.0%，最高 76.8%，
**没有任何区块超过 90%**。如果是全图快照，覆盖率应该接近 100%。
所以 `ModifiedOptimizedDataByDetailIndex` 记录的是「改动过的格子」，
只是层 9/10 的「改动」指的是加载，层 7/8 的「改动」才是铺地皮。

#### 14.4 真正的地皮在哪

#### 14.6 顺带查清的：区块编号 ↔ 游戏里的区块

玩家说「地表 75 号和在传送石列表的什么什么_7_4 是同一个区块（推测是第 8 行第 5 个区块）」。
验证结果：**推测正确**。

- 映射公式：`Index = BiomeY × 17 + BiomeX`，反解 `(BiomeX, BiomeY) = (Index % 17, Index / 17)`
- 17 是区块网格宽度。证明方式：`BiomeY = 1` 的传送石 BiomeX 为 1、2、3，
  对应模块 18、19、20（连续 ⇒ 宽度只能是 17）
- 营地锚点 区块(7,4) → `4 × 17 + 7 = 75` ✓
- 17 块传送石覆盖的 11 个不同区块，全部在存档里存在对应模块

世界坐标公式（17/17 传送石零误差）：

```
WorldX = 128 × (BiomeX × 150 + DetailX) + 64
WorldY = 128 × (BiomeY × 150 + DetailY + 1)
```

营地锚点 格(100,74) → 世界 (147264, 86400)。

## 十六、NPC 记忆模块（可读可改）

### 16.1 模块与结构

`NPCMemory__NPCMemoryData.sav`（26,190 B）只有一个根属性
`SavedNPCMemoryStorage`，四层嵌套：

```
SavedNPCMemoryStorage      Map<Name, struct>      NPC 名 -> 记忆
  └ MemoryByDay            Map<Int,  struct>      第几天 -> 当天记录
      └ EventGroups        Array<struct>          通常 1 个元素
          └ Events         Array<struct>          通常 1 个元素
              └ Type / Parameters / Priority      真正的条目，平铺重复
```

最内层那个「元素」其实是**把 N 条记录首尾相接塞进同一个属性表**，
所以一条记录 = 连续的三个属性。按 `Type` 开头、`Priority` 收尾切分即可。

实测：**35 位 NPC、282 天、2276 条事件**。

### 16.2 事件类型（`EMemoryEventType`）

枚举值是 FName 文本，写成 `EMemoryEventType::成员`：

| 成员 | 中文 | 含义 | 出现次数 |
|---|---|---|---|
| `Kill` | 击杀 | 击杀怪物 | 1095 |
| `MoodDeclined` | 心情下降 | 心情变差 | 937 |
| `Harvest` | 采集 | 采集到东西 | 180 |
| `Task` | 任务 | 接到/推进任务 | 53 |
| `Death` | 死亡 | 死亡过一次 | 11 |

### 16.3 Parameters 的键

`Parameters` 是 `Map<Name, Text>`，键里**有中文**：

| 键 | 出现次数 | 样例 |
|---|---|---|
| `NPCID` | 227 | `Assistant`、`Aurelia` |

### 16.4 修掉的一个解析 bug：Content 显示成 Priority

`Content` 的真实值是一段**空文本**，9 字节：

```
02 00 00 00 | FF 00 00 00 | 00 00 00 00
flags        history=None   长度 0 的 FString
```

但 `ParseSimple` 处理 map 标量 `TextProperty` 时没有长度可用，只能调
`ParseText(null)`——它按 `{9,10,5,6,4,0}` 顺序试前缀，取第一个读得出字符串的。
对空文本来说，skip=9 正好落在**下一个属性的名字** `Priority` 上，于是
`Content` 的值显示成了 `"Priority"`。

修法：`ParseMap` 解析完全部条目后，每个值的字节范围就确定了（从键尾到下一个键头）。
用这个精确长度重新解码一次（`ReadTextExact`），要求文本**恰好**在边界处结束；
对不上就返回空串。这样既修好了显示，也保证永远不会越界读到别人的属性名。

`没有房间` / `朴素的房间` 的值布局是第三种变体（前缀里带 4 字节 word，
且中文键的 KeyRaw 带负数 FName 号），仍然读不出内容，但它们本来也是空的。

### 16.5 能改什么、不能改什么

| 字段 | 类型 | 可改 | 说明 |
|---|---|---|---|
| `Priority` | IntProperty | ✅ | 整数，等长写入。数值越小越优先 |
| `Type` | EnumProperty | ✅ | FName 文本，**变长**写入（Task 27 B / Harvest 30 B） |
| `Parameters` | MapProperty | ❌ | 值的 FText 前缀长度在同一张 map 里都不统一，编码器写不了 |

为此在 `ValueEditor` 里新增了 `EncodeEnum`：把 `Task` 自动补成
`EMemoryEventType::Task`（否则游戏读成空枚举），并保留原值可能带的尾部 i32 号。
`IsEditable("EnumProperty")` 同时改为 `true`，`IsVariableLength` 也把它算进去，
交给补丁器去修正外层尺寸链。

### 16.6 界面

### 十七、营地移动为什么游戏不认（2026-11-14 夜 查清并修复）

第十三节说「把 `CampsiteCells` 每一格都平移」，当时以为这样就对了。
用户实测反馈：**改完进游戏，营地还在原地。** 这一节记录真正的根因。

#### 17.1 关键发现：那些字段是占位符，不是数据

把真实存档 `CampsiteCells` 的 6 241 格逐字段统计：

| 字段 | 真实存档里的值 | 说明 |
|---|---|---|
| `DetailX` / `DetailY` | 61..139 / 35..113 | **唯一有真实数据的两个字段** |
| `DetailIndex` | **−1**（6 241 格全部） | 占位符 |
| `CellIndex` | **−1**（6 241 格全部） | 占位符 |
| `LocalPosition` | **(0,0,0)**（6 241 格全部） | 占位符 |
| `WorldPosition` | **(0,0,0)**（6 241 格全部） | 占位符 |
| `BiomeX` / `BiomeY` | 7 / 4（全部相同） | 区块，不随格子变 |

也就是说：**这 6 241 格里，`DetailIndex`、`CellIndex` 和两个位置向量一个真值都没有。**
游戏在运行时按 `DetailX` / `DetailY` 加 `BiomeX` / `BiomeY` 自己算出来。

#### 17.2 旧代码做的事，正是把移动弄坏的原因

第十三节的实现会「顺带补全」这些字段：

```csharp
Put(F("DetailIndex"), ny * 150 + nx);          // -1 → 真实值
var b = ValueEditor.EncodeVector3(vp,
    (bx * 150 + nx) * 128.0 + 64,              // (0,0,0) → 真实坐标
    (by * 150 + ny + 1) * 128.0, ...);
```

实测（对副本，营地从 `(100,74)` 移到 `(120,90)`）：

| | 移动前 | 移动后（旧代码） |
|---|---|---|
| `DetailIndex = −1` | 6 241 / 6 241 | **0 / 6 241** |
| 位置全零 | 6 241 / 6 241 | **0 / 6 241** |
| `DetailIndex` 样例 | −1 | 11959, 12109, 12259 … |

填完之后，这块地皮的形状**和游戏自己写出来的存档不一样了**。游戏判定数据不一致，
把整个营地改动丢弃 —— 表现就是「编辑器里改了，进游戏没动」。

**结论：是「补全」这个动作本身破坏了移动，不是漏补。**
这一点和直觉相反，也是第十三节判断失误的地方：当时只验证了「锚点和占格一起动」，
没有验证「动完之后的字节形态是否仍然是游戏认可的形态」。

#### 17.3 修法

`ShiftCampsiteCells` 只平移 `DetailX` / `DetailY`，其余字段原样保留：

```csharp
Put(px, nx);
Put(py, ny);
// CellIndex / DetailIndex / 两个位置向量保持游戏自己写的占位符（-1 和 0）
```

#### 17.4 验证

对副本移动 6 241 格，`X 61..139 / Y 35..113` → `X 81..159 / Y 51..129`：

| 检查项 | 结果 |
|---|---|
| `DetailIndex = −1` | 6 241 / 6 241 ✅ |
| `CellIndex = −1` | 6 241 / 6 241 ✅ |
| 位置全零 | 6 241 / 6 241 ✅ |
| 格范围平移 | +20 / +16，精确 ✅ |
| 锚点 | 同步更新 ✅ |

来回移动三次 `(100,74) → (120,90) → (70,50) → (100,74)`，坐标全部精确回到原位，
说明平移是可逆的、没有累积误差。

`--selftest` 营地一项：`位置 (100,74) → (120,90)`，重开验证 `(120,90)（期望 (120,90)）→ 通过`。

#### 17.5 `CellIndex` 为什么不动（补充第十三节）

`CellIndex = BiomeY × 17 + BiomeX`。营地是 `Biome(7,4)`，`4×17+7 = 75` ✅。

这个值只跟**区块**走，与格子在区块内的位置无关，所以同区块内平移不该改它。
跨区块移动才需要重算 —— 当前版本不支持跨区块移动。

#### 17.6 顺带修掉的两个真实 bug

**(1) `ParseStructMapKey` 把 16 字节 GUID 键当成 8 字节整数对**

`BedRegistry` 和 `CoordToAutoZoneMap` 的键是 GUID。解析器只读 8 字节当
`(i32,i32)`，导致 key 和 value 错开一半：`BedRegistry` 的 9 条全部读不出键，
`CoordToAutoZoneMap` 的 14 条裂成 28 条「只有键 / 只有值」的碎片。

修法是**结构对齐判断**而不是数值猜测：分别试读 8 字节和 16 字节，
看哪种读法让游标落在合法的属性 tag 上。第一版用「数值范围像不像坐标」来猜，
结果把宝箱数从 138 改成了 141 —— 猜测会悄悄改变别的模块的解析结果，
这是不能接受的，所以改成了结构判断。修后 `BedRegistry` 9 条全部正确，
宝箱数回到 138。

`CoordToAutoZoneMap` 首条键确实是属性表（9 个字段）而非 GUID，仍读不完整；
但这个字段编辑器完全没用到，不影响任何功能。

**(2) 记忆页整页空白**

`BuildMemory` 把详情塞进一个 `Height = 1` 的子 Panel，Panel 在加入容器后才长高，
滚动容器不会重新计算范围，于是详情卡全部落在可视区之外 —— 页面下半截是空的。

改成和其它页一致的**整页重建**。第一次改完直接崩了：

```
Win32Exception (1158): 创建窗口句柄时出错。
   at MainForm.StackCards(...)
   at MainForm.BuildMemory()
   at ListView.OnSelectedIndexChanged(...)
```

在 `ListView` 自己的 `SelectedIndexChanged` 里同步 `Navigate`，等于在控件派发自己的
通知时把它销毁 —— 和之前地图页 `ComboBox` 崩溃同一类问题。用 `BeginInvoke` 把重建
排到消息队列之后即可。

#### 17.7 这一节的教训

**「看起来更完整」不等于「游戏认」。**
补全占位符在语义上像是把数据修对了，实际上破坏了游戏认可的字节形态。
验证一个编辑是否成功，不能只比对「读回来的值对不对」，
还要比对「没打算改的字段有没有被顺带改掉」。


### 十八、编辑「改完不显示」的三个根因（2026-11-15 查清并修复）

用户反复反馈「无法赋新值」。查下来不是一个 bug，是三个，而且都出在
「编辑之后怎么把新值读回来」这条路上。

#### 18.1 `MarkDirty` 只暂存，读的人却读旧值

`SaveProperty.MarkDirty(bytes)` 并不改 `Value`，它把新字节放进 `PendingValue`，
等 `SaveAll` 时统一重建。所以任何「编辑后立刻显示」的地方都必须读
`ValueEditor.EffectiveValueOrNull(p)`，而不是 `p.Value`。

`SaveFacade` 里三个基础读取函数当时读的是 `p.Value`：

| 函数 | 影响的字段 | 症状 |
|---|---|---|
| `F()` | 玩家 `MaxHealth`、`CurrentHealth`、全部 NPC 血量/魔力 | 改完血量还是老数字 |
| `D()` | 全部双精度浮点字段 | 同上 |
| `S()` | `PlayerName`、`CampsiteName`、`TrackedQuest`、`SkinID` | 改完名字还是老名字 |

这三个改成 `EffectiveValueOrNull` 之后，营地名、玩家名、玩家最大生命、
NPC 血量全部做到「改完立刻看得见」。

#### 18.2 `DecodeForType` 漏了 `EnumProperty`

`DecodeForType` 负责把刚写进去的字节解回可显示的值，它的字符串分支只列了
`StrProperty` / `NameProperty` / `TextProperty`。而 NPC 记忆的 `Type` 是
**`EnumProperty`**（值形如 `EMemoryEventType::Kill`），于是走到 `default:
return previous`——永远返回旧值。

后果：`SetType` 明明写成功了，界面刷新后还是原来的类型，看起来就是「改了没用」。
把 `EnumProperty` 加进字符串分支即可（它的值就是一个 FName 体，没有额外前缀）。

#### 18.3 地形对话框读了输入框，但从来没使用

`BuildTerrainDialog` 里建了「图块集」和「图块」两个 `NumericUpDown`，
`Apply()` 里却只处理了放置物的朝向和旋转，**两个数字框根本没被读过**。
所以在对话框里填了新图块、按「确定」，什么都不会发生——
这正是用户说的「无法赋新值，不是改了不生效」。

修好后 `Apply()` 先比较两个框与当前值，不同就调 `ChunkFacade.SetTerrainTile`。

#### 18.4 三个 bug 的共同点

都是**写入路径正确、回读路径断掉**。存档文件其实一直是改对的，
所以「保存后重新打开存档看」能看出变化，而「改完当场看界面」看不出。
这也解释了为什么早期几次修复都没打中要害——我一直在检查写入，没有检查回读。

**回归测试**（`GenerativeSave.Verify`，对副本跑，26 项）

| 项 | 结果 |
|---|---|
| 存档名 / 营地名 / 玩家名 / 营地等级 | 改完立即读到新值 |
| 玩家最大生命 606 → 999 | 通过 |
| 背包数量 999 → 42 | 通过 |
| NPC 血量 1.00 → 0.50 | 通过 |
| 记忆 Type `Task` → `Kill` | 通过（对象上和重读都变） |
| 记忆 Priority 1 → 9 | 通过 |
| 地形层 7/8/9/10 各改一格 → 57-7 | 通过，记录数仍 5071 |
| 保存后重开：存档名/营地名/等级/血量/NPC 63/宝箱 138/区块 5071 | 全部复原 |

**失败 0 项。**

### 十九、营地能移多远：79×79 地皮决定了安全范围（2026-11-15 补）

营地不是「一个点」，是**以锚点为中心的 79×79 地皮**，实测占格范围恒等于
`锚点 ± 39`：

| 锚点 | 占格 X | 占格 Y |
|---|---|---|
| (100,74) | 61..139 | 35..113 |
| (39,39) | 0..78 | 0..78 |
| (110,110) | 71..149 | 71..149 |

一个区块只有 150×150 格，所以锚点一旦小于 39 或大于 110，地皮就会伸到区块外面。
游戏对这种越界位置**不报错，直接忽略**——玩家看到的就是「改了位置，营地没动」。

旧版对话框写的是「格坐标 0–4095」，`SetCampsitePosition` 也只校验 0–4095，
于是用户完全可以填一个游戏不认的值，程序还显示成功。这是「营地移不动」
反馈里一直没被识别的一种情况。

**现在**：`SetCampsitePosition` 只接受 39–110，越界直接返回带解释的错误；
对话框的说明文字和输入框范围也同步改成 39–110。

**验证**（对副本，14 项）

| 输入 | 结果 |
|---|---|
| (5,74) (74,5) (120,74) (74,120) (0,0) (149,149) | 全部拒绝，提示「应在 39–110 之间」 |
| (39,39) (110,110) (74,74) (39,110) (110,39) | 全部成功，占格始终落在 0..149 内 |
| 保存后重开 | 位置复原，占格仍 6 241 |

### 二十、玩家没有魔力上限和饥饿上限字段（2026-11-15 补）

查「全部回满为什么回不满魔力」时顺带把玩家属性翻了一遍。`PlayersData` 里 39 个属性，
和状态相关的只有这些：

| 属性 | 值 | 有上限吗 |
|---|---|---|
| `CurrentHealth` / `MaxHealth` | 1037 / 606 | 有 |
| `CurrentMagic` | 400 | **没有上限字段** |
| `CurrentHunger` | 93.18 | **没有上限字段** |
| `CurrentHeat` / `MaxHeat` | 100 / 100 | 有 |
| `CurrentToxin` / `MaxToxin` | 0 / 100 | 有 |

也就是说魔力满值 400、饥饿满值 100 是**游戏里写死的**，存档不存这两个上限。
旧版「全部回满」照着 `MaxMagic` / `MaxHunger` 去找，找不到就退回读当前值，
写了个空操作，所以魔力、饥饿一直回不满。

NPC 那边不一样：`GenCharacter` 的 `AttributeMap` 里 `MaxMana` 是真实字段
（样本「春水之灵 绯樱」= 435），并且已经在界面上可编辑。玩家的 `MaxMagic`
在整个存档里不存在——这不是漏读。

### 二十一、数量为 0 的物品格是「幽灵格」（2026-11-15 补）

`AddItemToPlayer` 原来只校验「有没有空槽」，不校验数量。传 0 或负数进去，
它会正常写一格：物品 ID 是真的，数量是 0。

这种格子在游戏里看起来是空的，但**槽位确实被占着，而且清不掉**——
既不显示成可拾取的物品，也不会被判定为空槽。等于永久吃掉一个背包格。

现在入口直接拒绝非正数量。界面上本来就有 `count <= 0` 的判断，
但那是唯一一道防线；底层补上以后，任何调用路径都不会再产生幽灵格。

### 5. 「全部回满」不会回满魔力和饥饿

### 7. 所有布尔字段改完读不到新值（最后一个，也是最广的一个）

**症状**：放置物的「90 度翻转」改完，界面还是原来的状态。

**原因**：`BoolProperty` 的值存在属性标签头里，所以 `MarkBool` 暂存的是
`PendingBool`，而不是 `PendingValue`。但 `EffectiveValue` 只看 `PendingValue`：

```csharp
if (!p.IsDirty) return p.Value;
return DecodeForType(p.TypeName, p.PendingValue!, p.Value);   // PendingBool 被忽略
```

`IsDirty` 对两者都返回 true，于是走进这个分支，却拿 `PendingBool` 为 null 的
`PendingValue` 去解码——退回旧值。

**影响面**：所有走 `MarkBool` 的编辑。不只是放置物翻转，词条对话框里两个
「启用」勾选框也是这条路。

**修法**：`EffectiveValue` 先看 `PendingBool`，有就返回它。

**验证**：Turn90 False → **True**，改完立刻读得到。

> 这是这一轮修的第 7 个、也是波及面最广的一个「改完读不到」bug。
> 前六个分别出在字符串、浮点、枚举、地形对话框、营地范围和数量校验上。

### 十一、资料库导出 / 导入（本轮新增功能）

#### 11.1 你要的格式

`Base64` → `ASCII→16进制` → `UTF-8→二进制` → **1~2位叠数计量法**。

实现在 `GenerativeSave.Core\Library\LibraryCodec.cs`。导出链路是：

```
catalog JSON → UTF-8 字节 → Base64 文本 → 每个字符转两位十六进制
→ 十六进制文本的 UTF-8 字节 → 位串 → 叠数计量法
```

导入是严格逆运算：叠数 → 位串 → 字节 → 十六进制文本 → Base64 → JSON。

#### 11.2 叠数计量法的规则

位串按游程写成一串计数，**计数之间没有分隔符**。首段是 1；如果实际是 0，
开头先写一个字面 `0` 当标记。

| 计数 | 写法 | 例子 |
|---|---|---|
| 1~9 | 1 位数字 | `3` |
| 10~549 | 字母 + 1 位数字 | `A2` = 12、`A0` = 10 |
| 超过 549 | `@9` + `0` + 余数 | `@903` = 552 |

字母表：`A`~`Z` = 10~260，`a`~`z` = 270~520，`%` = 530，`@` = 540。

**`0` 是「本游程继续」的截断标记，不是一个计数。** 这就是下面两个的区别：

- `@93` = `@9`（549 个 1）+ `3`（3 个 0）→ **549 个 1 + 3 个 0**
- `@903` = `@9`（549）+ `0`（没翻转，继续）+ `3` → **552 个连续 1**

你给的四条例子全部对上：

```
111000111111110000        → 3384
00111111111111000000111   → 02A263
10001111001               → 13421
0000000000                → 0A0
```

#### 11.3 UI

资料库页新增两个按钮：

- **导出资料库…**：显示密文，可「复制全部」或「另存为文件…」。
- **导入资料库…**：粘贴或「从文件读取…」，导入后合并。

导入是**合并**不是覆盖：只补本地没有的 ID，不会用别人的名字盖掉你已经录入的。
重复导入同一份密文零新增。导入时会自动剔除非官方行。

### 十二、物品描述与属性编辑（V20）

#### 12.1 起因

群里有人说能改物品描述和属性，而我这版只能改数量——「甚至有些参数改了不生效」。

#### 12.2 摸到的真相

**描述文字本来就在存档里。** 之前把它当成 GUID 忽略了：UE 的 `FText` 在字符串表引用后面还挂着一串 UTF-16 正文，那才是人读的那段话。

`3010046` 大棒骨的 `Desc` 共 89 字节：

```
00 00 00 00  00 01 00 00 00 00  21 00 00 00
"25595E6A4E2164BDCBB0F3B546055702" 00
ED FF FF FF  <UTF-16 "重击地面。技能：在前方依次升起岩刺。">  00 00
```

前半截是表引用（flags / history / 表名 / GUID），后半截 `ED FF FF FF` 是负长度，表示后面是 UTF-16 正文。把负长度这条分支补上，50 件物品的说明全部解出来了，和你截图逐字一致。

#### 12.3 「改了不生效」的真正原因

`ItemConfig.EquipmentAttributeMap` 里两种值混在一起：

| 类型 | 例子 | 改 Value 有效吗 |
|---|---|---|
| 扁平值 | `CritRate 0.30`、`AttackRange 0.69` | **有效** |
| 曲线值 | `PhysicalDamage`，`CurveTable=ItemAttrCurveTable`，`RowName=3010046_PhysicalDamage` | **无效** |

曲线值的 `Value` 只是倍率，真实数字由曲线行按**等级**算出来。存档里 `PhysicalDamage.Value = 1`，游戏里却显示 **99 攻击力**——就是这个原因。编辑器以前照样让你改，改完读档被重算覆盖，看起来就是「没生效」。

现在带曲线的属性显示为灰色，旁边写明曲线行，要改只能改词条等级。

#### 12.4 群里那条消息带来的关键修正

原计划是把官方道具的 `Desc` 改写成内联 `FText`。消息指出：**官方道具的说明和词条是加密数据表引用，改写会坏档；AI 物品才有完整字段定义。**

核对存档，完全对得上：

| | 官方道具（7 位 ID） | AI 道具（8 位 ID） |
|---|---|---|
| `ItemName` / `Desc` | 字符串表引用（65~436 字节） | 内联文本（23~101 字节） |
| 定义来源 | 游戏 `DT_Items` 数据表 | 存档本身 |
| 读档行为 | 用数据表重建 | 原样读取 |
| 编辑后果 | 被覆盖 / 可能坏档 | 正常生效 |

所以立刻改成按 ID 长度分流：

- **AI 道具**（`ItemId.Length >= 8`）：名称、描述、属性、词条全部可改。
- **官方道具**：只能改数量；其余字段只读显示。

### 三种原因

#### 1. 填的数超过了堆叠上限（最常见）

每件物品在存档里带一个 `MaxStack`：

| 物品 | 上限 |
|---|---|
| 沙漠石头 1020051 | 999 |
| 烤肉排 1010007 | 99 |
| 营地卷轴 1020057 | 99 |
| 复活灵药 1020034 | 99 |

**编辑器能如实写进 1200**（我实测磁盘上确实是 1200），
但**游戏读档时会按上限夹回 999**。从你的角度看，就是「改了，进游戏又变回去」。

**现在已修**：对话框里填超过上限的数，会当场弹窗告诉你上限是多少，
并把输入框夹回上限，不会写一个注定活不过一次读档的值。

> 真想超过上限，只能多占几个格子：用「复制一组」。

#### 2. 改的时候游戏还开着

游戏退出时会用内存里的整份数据覆盖存档。你反馈之前 18 秒，
存档被整体重写了一次（10:37:06，所有模块时间戳一模一样）——那是游戏自己写的。

**编辑器已经会检测**：载入时如果发现游戏在跑，会弹窗让你先关掉；
保存时也会再问一次。

#### 3. 游戏读的是版本快照，不是 Primary

`Versions\v_<版本号>\Modules\` 里有 3 份完整副本，
`Manifest.sav` 的 `ActiveVersion` 指向哪一份，游戏就读哪一份。

编辑器保存时会**自动把这些快照一起同步**（保存报告里会写「同步 N 份快照」）。
如果你的报告里没有这一行，说明快照没同步上，告诉我。

---

### 现在保存后会做回读校验

以前保存完只告诉你「已保存 N 个文件」——那只证明字节动了，不证明值生效了。

现在保存后会**重新从磁盘打开存档，逐个比对刚改过的物品数量**：

- 全部对上 → 「数值已确认写入」
- 有对不上的 → 弹窗列出具体是哪个物品、期望多少、磁盘上是多少，
  并提示先关游戏重试

所以以后如果还回退，你会**当场看到是哪个值没落地**，而不是进游戏才发现。

### 正确的操作顺序

1. **先完全退出游戏**（不是退到主菜单，是关掉进程）
2. 打开 `发布版\存档编辑器.exe`
3. 改数量（不要超过上限，超了会拦你）
4. 点「保存修改」
5. 看弹窗：确认出现「数值已确认写入」
6. 再启动游戏

---

### 如果想验证某次修改到底写没写进去

保存报告里会列出：
- 每个文件的「旧大小 → 新大小」和写入时间
- 从磁盘读回的当前值（存档名、玩家名、背包前几件）
- 同步了哪几份快照

文件在：`%LOCALAPPDATA%\GenerativeSaveEditor\backups\`（原文件都在，可随时回滚）
